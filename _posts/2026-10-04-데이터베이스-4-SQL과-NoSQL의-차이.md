## 1. 개요

애플리케이션은 회원 정보, 주문 내역, 게시글처럼 계속 늘어나는 데이터를 안전하게 저장하고 다시 찾아야 한다. 이때 자주 비교하는 선택지가 **SQL 데이터베이스**와 **NoSQL 데이터베이스**다.

SQL은 보통 정해진 구조의 테이블을 관계로 연결해 다루는 관계형 데이터베이스를 뜻한다. NoSQL은 테이블과 SQL만을 중심으로 하지 않는 여러 데이터베이스 모델을 묶어 부르는 말이다. 둘 중 하나가 항상 더 좋은 것은 아니며, 데이터의 모양과 조회·변경 방식에 따라 적합한 선택이 달라진다.

---

## 2. SQL: 테이블과 관계를 중심으로 저장하기

SQL(Structured Query Language)은 관계형 데이터베이스에 데이터를 정의하고 조회·변경할 때 쓰는 언어다. 관계형 데이터베이스는 행(row)과 열(column)로 구성한 테이블에 데이터를 저장한다.

예를 들어 쇼핑몰에서는 회원과 주문을 별도 테이블로 나누고, 주문의 `member_id`로 회원을 가리킬 수 있다. 이때 열의 이름과 자료형을 미리 정한 구조를 **스키마(schema)** 라고 한다.

| members 테이블 | orders 테이블 |
| --- | --- |
| `member_id`, `name`, `email` | `order_id`, `member_id`, `amount` |

회원의 주문 목록을 보고 싶다면 `JOIN`으로 두 테이블을 연결한다. 다음 쿼리는 주문과 주문한 회원의 이름을 함께 조회한다.

```sql
SELECT o.order_id, m.name, o.amount
FROM orders AS o
JOIN members AS m
    ON o.member_id = m.member_id;
```

SQL 데이터베이스는 기본키, 외래키, `NOT NULL` 같은 제약 조건으로 데이터 규칙을 데이터베이스 수준에서 표현하기 좋다. 결제처럼 여러 데이터가 함께 정확히 바뀌어야 하는 기능에도 자주 사용한다.

---

## 3. NoSQL: 데이터 형태에 맞는 모델 고르기

NoSQL은 "SQL을 전혀 쓰지 않는다"는 뜻이라기보다, 관계형 테이블 외의 방식으로 데이터를 저장하는 데이터베이스를 가리킨다. 제품마다 제공 기능은 다르지만, 대표적인 모델은 다음과 같다.

| 모델 | 저장 방식 | 어울리는 데이터 예 |
| --- | --- | --- |
| 문서(Document) | JSON과 비슷한 문서 단위 | 게시글과 댓글, 상품 정보 |
| 키-값(Key-Value) | 키 하나에 값 하나를 연결 | 세션, 캐시 |
| 와이드 컬럼(Wide-column) | 행마다 열 구성이 달라질 수 있는 구조 | 대량 이벤트·로그 |
| 그래프(Graph) | 노드와 관계를 직접 저장 | 친구 관계, 추천 관계 |

문서 데이터베이스에는 한 상품을 다음처럼 하나의 문서로 저장할 수 있다. `options`처럼 상품마다 달라지는 정보를 같은 문서 안에 넣기 편하다.

```json
{
  "name": "티셔츠",
  "price": 29000,
  "options": {
    "colors": ["black", "white"],
    "sizes": ["S", "M", "L"]
  }
}
```

NoSQL은 데이터 구조를 바꾸기 쉬운 경우가 많지만, 스키마가 아예 없는 것은 아니다. 애플리케이션이 어떤 필드를 저장하고 읽을지 정해야 하며, 제품에 따라 스키마 검증 기능도 제공한다. 구조가 유연하다는 점은 빠른 변경에 도움이 되지만, 데이터 형식이 제각각이 되지 않도록 규칙을 관리해야 한다.

---

## 4. 핵심 차이 비교

SQL과 NoSQL의 차이는 단순히 명령어 문법의 차이가 아니다. 데이터를 어떤 구조로 표현하고, 여러 서버에 어떻게 나누며, 일관성을 어느 수준으로 보장할지까지 함께 고려해야 한다.

| 관점 | SQL 데이터베이스 | NoSQL 데이터베이스 |
| --- | --- | --- |
| 대표 구조 | 행과 열로 된 테이블 | 문서, 키-값, 와이드 컬럼, 그래프 등 |
| 데이터 관계 | 외래키와 `JOIN`으로 명확하게 표현 | 모델에 따라 문서에 함께 저장하거나 참조로 연결 |
| 스키마 | 보통 열과 자료형을 미리 정의 | 모델에 따라 더 유연하게 변경 가능 |
| 일관성·트랜잭션 | 여러 테이블을 묶는 트랜잭션과 제약 조건에 강점 | 지원 범위와 방식이 제품마다 다름 |
| 확장 방식 | 서버 성능을 높이는 확장부터 시작하는 경우가 많음 | 데이터를 여러 서버에 분산하는 구조를 고려한 제품이 많음 |

위 표는 일반적인 경향이다. 관계형 데이터베이스도 읽기 복제나 샤딩으로 여러 서버에 확장할 수 있고, NoSQL 데이터베이스도 트랜잭션과 강한 일관성을 제공할 수 있다. 따라서 이름만 보고 성능이나 기능을 단정하면 안 된다.

---

## 5. 언제 선택할까?

먼저 데이터와 기능의 요구 사항을 기준으로 판단한다. 예를 들어 주문, 재고, 결제처럼 여러 레코드의 변경이 반드시 함께 성공하거나 실패해야 하고 테이블 간 관계가 복잡하다면 SQL 데이터베이스가 자연스러운 출발점이 될 수 있다.

반대로 게시글마다 필드 구성이 자주 달라지는 콘텐츠, 매우 빠르게 읽어야 하는 세션·캐시, 관계를 중심으로 탐색하는 추천 기능은 각각의 데이터 형태에 맞는 NoSQL 모델이 편할 수 있다. 한 서비스 안에서 SQL과 NoSQL을 함께 사용하는 경우도 흔하다. 주문 원장은 SQL에 두고, 로그인 세션은 키-값 저장소에 두는 식이다.

선택 전에 다음 질문을 확인하면 좋다.

- 데이터 간 관계를 조인으로 자주 조회하는가?
- 여러 데이터를 한 번에 정확히 변경해야 하는가?
- 데이터 필드가 자주 달라지거나 항목마다 모양이 다른가?
- 가장 많은 읽기·쓰기 요청은 어떤 형태이며, 얼마나 빠르게 처리해야 하는가?
- 운영할 팀이 해당 데이터베이스의 백업, 복구, 모니터링을 감당할 수 있는가?

특히 "NoSQL이므로 항상 빠르다"거나 "SQL은 확장할 수 없다"는 식의 판단은 피해야 한다. 데이터 모델과 인덱스, 쿼리 방식, 운영 환경이 실제 성능에 더 큰 영향을 준다.

---

## 6. 정리

SQL 데이터베이스는 테이블, 관계, 제약 조건을 중심으로 정형화된 데이터를 안전하게 다루는 데 적합하다. NoSQL은 문서·키-값·그래프처럼 다양한 모델을 제공해 데이터의 모양과 접근 방식에 맞춰 설계할 수 있다.

중요한 것은 유행하는 이름을 고르는 일이 아니라, 데이터 관계와 일관성 요구 사항, 주된 조회 패턴을 먼저 이해하는 것이다. 요구 사항을 작게 정의한 뒤 실제 쿼리와 데이터 양으로 검증하면 더 적절한 데이터베이스를 선택할 수 있다.
